# Security Policy

## Reporting a Vulnerability

If you find a security vulnerability in Rumi Messenger, please report it responsibly.

**Do not open a public GitHub issue for security vulnerabilities.**

Preferred channel: open a private report via [GitHub Security
Advisories](https://github.com/Orenda-Project/rumi-messenger/security/advisories/new). The
maintainer team is notified automatically.

Forks: replace this section with your own intake (a private email address, or your fork's GitHub
Security Advisories tab) before you put this repository in front of a user-facing audience.

Include:
- Description of the vulnerability
- Steps to reproduce
- Affected component (`deploy/`, `scripts/`, or the Matrix channel driver in `rumi-platform`)
- Any potential impact assessment

## Response Timeline

- **Acknowledgment**: within 48 hours
- **Initial assessment**: within 5 business days
- **Fix timeline**: depends on severity, typically within 30 days for critical issues

## Scope

In scope:
- `deploy/` -- the Compose stack, homeserver configuration, and Element Web config/branding
- `scripts/` -- `setup.sh`, `e2e.sh`, `backup.sh`, `reset.sh`, `logs.sh`, `connect-rumi.sh`
- The Matrix channel driver in `rumi-platform` (`bot/shared/services/messaging/matrix-*`), for
  anything that reaches this repo's deploy or integration path

Out of scope:
- Synapse and Element Web themselves (report upstream: [matrix.org
  security](https://matrix.org/security-disclosure-policy/), [element-hq/element-web
  security](https://github.com/element-hq/element-web/security))
- Third-party services (Docker Hub, your DNS/TLS provider)
- Issues requiring physical access to your infrastructure
- Social engineering attacks

## What secrets exist, and where

This stack generates and stores real secrets on first run. Know where they are before you deploy
for real:

| Secret | File | Notes |
|---|---|---|
| Postgres password | `deploy/.env` (`POSTGRES_PASSWORD`) | generated by `scripts/setup.sh` if left blank |
| `@rumi` bot password | `deploy/.env` (`RUMI_BOT_PASSWORD`) | generated by `scripts/setup.sh` if left blank |
| Admin password | `deploy/.env` (`ADMIN_PASSWORD`) | printed once at the end of `setup.sh`, never stored elsewhere in plaintext |
| Registration shared secret | `deploy/.env` (`REG_SHARED_SECRET`) | also written into `homeserver.yaml`; used to mint the admin API HMAC |
| Homeserver secrets (`registration_shared_secret`, `macaroon_secret_key`, `form_secret`) | `deploy/synapse/data/homeserver.yaml` | |
| Signing key | `deploy/synapse/data/<server_name>.signing.key` | identifies your homeserver to other servers if you ever federate |
| Bot access token, for rumi-platform | `deploy/rumi-channel.env` | consumed by `scripts/connect-rumi.sh`; never printed to a terminal by that script |

All of the above are gitignored. **None of them should ever be committed.**

## The chmod 600 rule

`scripts/setup.sh` sets `deploy/.env`, `deploy/rumi-channel.env`, `homeserver.yaml`, and the
signing key to mode `600` (owner read/write only) as the last step of writing each one. If you
add a new secret file to this stack, do the same -- `chmod 600 <file>` right after you write it,
not as an afterthought. `scripts/connect-rumi.sh` follows the same rule for the `.env` it writes
into a target rumi-platform checkout.

## Safe Harbor

We consider security research conducted in good faith to be authorized. We will not pursue legal
action against researchers who:

- Make a good faith effort to avoid privacy violations, data destruction, or service disruption
- Only interact with deployments they own or have explicit permission to test
- Report vulnerabilities promptly and do not exploit them beyond what is necessary to demonstrate
  the issue

## Security Practices

This project follows these practices:
- No credentials committed to the repository (`.gitignore` covers every generated secret file)
- Environment variables for all secrets (`deploy/.env.example` documents every one)
- Registration is `open` by default for local testing; switch `REGISTRATION_MODE=token` before
  exposing a deployment publicly (see [docs/RUNBOOK.md](docs/RUNBOOK.md))
- Synapse and Element ports bind to `127.0.0.1` by default -- nothing is reachable off the host
  until you put Caddy (or your own reverse proxy) in front of it with real TLS
- End-to-end encryption on the client side (Olm/Megolm) means the homeserver stores ciphertext,
  not message content, for encrypted rooms
